# Bridge - Into Part II

Part II shifts from structural grammar to historical practice.

## Why Software Comes Next

Part I defined the problem: responsibility must remain cohesive, consequence must remain intentionally coupled, and scale plus abstraction make both harder. Part II turns to software because software delivery exposes these structural variables with unusual clarity and speed.

In software history, method changes are not only cultural stories. They are design responses to consequence distance. Each shift changes who decides, when feedback returns, and whether learning reaches the boundary that can redesign behavior.[^p2b-method-history]

## What This Part Tests

This part treats software as an early laboratory for the full book's claim:

- **Waterfall** as long-loop temporal coupling.
- **Agile** as a partial restoration of team-level cohesion.
- DevOps as operational recoupling between builders and runtime consequence.
- **DORA** as measurable signal about learning-loop quality.
- Shift-left practice as temporal compression of correction.[^p2b-dora]
- Each method as a response to coordination pressure when independently evolving teams, services, or release stages must still produce a coherent outcome.

The aim is not nostalgia or methodology advocacy. The aim is to show, in concrete sequence, how systems move when consequence arrives too late, and how they recover when consequence returns sooner.

## How to Read the Sequence

Read these chapters as structural experiments rather than winners-and-losers debates. Each method improves some coupling/cohesion dimensions while introducing new tradeoffs at scale.

By the end of Part II, the reader should be able to track software practice changes as governance changes in miniature: who can decide, who absorbs cost, and how quickly reality forces redesign.

Chapter 5 begins with Waterfall, where long planning horizons and late integration often produce low temporal coupling between design decisions and operational consequence.
